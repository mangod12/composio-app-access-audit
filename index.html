Prioritize by the access path, not the logo.

Start with narrow, testable tools.

Telegram bots, free-plan Asana workflows, Fathom meeting data and Grain personal tokens have documented developer paths. Start read-only, then expand scope.

Free personal access does not imply workspace-wide access or free production usage.

Separate prototype from rollout.

Plaid and QuickBooks offer development environments. That does not settle production approval, customer consent, subscription costs or real-money permissions.

Record sandbox and production as separate fields, never one yes/no flag.

Queue outreach before code.

Waterfall requires contacting the team. PitchBook needs an API contract. LinkedIn Ads starts with an approval process. An OAuth implementation does not remove these gates.

A public reference is evidence of an API, not evidence of self-serve credentials.

MCP needs a type, not a checkbox. Twilio has a documentation-only MCP. Neo4j has a database-action server. Shopify's general server is marked coming soon, separate from storefront WebMCP. Sherlock and Mermaid are local tools that need controlled wrappers.

Other recurring risks: personal versus organization credentials, admin installation policies, per-product auth, paid feature entitlements, and outdated migration guidance. Every row keeps the blocker beside the proposed path.
